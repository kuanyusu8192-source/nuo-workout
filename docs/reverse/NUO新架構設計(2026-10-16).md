# NUO 新架構設計（2026-10-16）

> 依據：[[VolumeX功能盤點(2026-10-16)]]。目標是把 nuo-workout 由單檔 HTML 改寫為 Android APK，吸收 VolumeX 的功能，並保留 NUO 自己的特色。
> 狀態：設計已逐題確認（九題），尚未建立程式碼、尚未動 nuo-workout repo。

## 1. 已確認的決定

| # | 主題 | 決定 |
|---|---|---|
| 1 | 動作 GIF | GIF **不進 git**，放本機資料夾，建置時複製進 APK（約 369 MB，自用側載）。 |
| 2 | 動作庫合併 | NUO 原有約 40 個動作（含收操伸展）併入同一份庫，來源標「自訂」，新增「伸展／收操」分類。 |
| 3 | 身體資料 | **首次開啟跑完整三步問卷**（性別年齡身高體重 → 活動量 PAL → 目標）。 |
| 4 | 記錄流程 | 統一成「今日訓練」一種流程；**每組填完就存**；可隨時加動作；可從課表／週計畫一鍵帶入。 |
| 5 | 週計畫 | 「週計畫」為一等公民（星期 → 課表範本）；可有多套（器材版、出差版），切換＝出差模式；首頁顯示今日課表。習慣鏈格子不保留，由全年日曆取代。 |

| 8 | 消耗估算 | 標準算法：kcal = MET × 體重 × 小時；重訓固定 MET（預設約 5.0，可調）；跑步／走路用 ACSM；其他有氧查 MET 表；保留手動覆寫（留空＝恢復自動）。 |
| 9 | 交付 | **B：先完成資料層與所有畫面框架，再整合**（使用者指定，與建議方案 A 不同）。 |

## 2. 範圍

**納入**：訓練記錄、動作庫、歷史與統計、全年日曆、課表範本與進行中訓練、週計畫（器材／出差）、新人計畫、體重與體脂、飲食（TDEE、營養目標、手動輸入、份量、收藏、日曆）、運動消耗與開關、Hevy／Strong 匯入、設定、收操建議。
**排除（使用者明確指定）**：AI（教練、菜單、照片辨識）、飲水、HYROX、社群（好友、動態牆、群組、排行榜、稱號社交）、條碼掃描與查詢、食物搜尋。
**不做**：付費牆與免費版限制（7 天歷史、課表上限 6、月／年圖表上鎖）。登入與雲端同步。

## 3. 技術選型

| 層 | 選擇 | 理由 |
|---|---|---|
| 建置 | Vite + TypeScript（strict） | 模組化、型別保護資料模型 |
| UI | Preact（含 hooks） + 少量自寫元件 | 體積小，手機 WebView 順暢 |
| 資料 | IndexedDB（Dexie） | 容量大、可查詢、事務性 |
| 圖表 | uPlot 或輕量自繪 SVG | 柱狀與折線圖為主 |
| 封裝 | Capacitor（Android） | 背景通知、震動、螢幕常亮、分享選單、檔案 |
| 測試 | Vitest（資料層與統計純函式）＋ 幾個 UI 整合測試 | 統計與算式是出錯高風險區 |
| 安裝 | `adb install -r`（無線偵錯已驗證可用） | 自用、不上架 |

## 4. 資料模型（IndexedDB）

```
exercises        id, name, nameEn, category, bodyPart, equipment, primaryMuscle, secondaryMuscles[],
                 trackingType('strength'|'cardio_*'|'stretch'), steps[], tips, gifFile, source('volumex'|'custom'|'nuo')
sessions         id, date(YYYY-MM-DD), startedAt, endedAt?, templateId?, planId?, mode('gear'|'travel'|'backfill'), note?
sets             id, sessionId, exerciseId, setIndex, weightKg?, reps?, durationSec?, distanceM?, speed?, incline?, watts?, floors?, createdAt
templates        id, name, color, exercises[{exerciseId, targetSets, targetReps?}], cooldownText?, createdAt
plans            id, name('器材版'|'出差版'|…), days{0..6: templateId|null}, isActive
bodyMetrics      id, date, weightKg?, bodyFatPct?
profile          id=1, sex, age, heightCm, weightKg, pal, goal('cut'|'maintain'|'bulk'), tdee, kcalTarget, macros{p,c,f}
meals            id, date, name, per100g?, grams?, servings, protein, carb, fat, kcal, photo?
favoriteMeals    id, name, protein, carb, fat, kcal
favoriteExercises exerciseId
burnOverrides    date, kcal
settings         weightUnit, loadUnit, restDefaultSec, countBurnToBudget, healthConnect, locale, metStrength, theme…
```

**原則：所有統計都從 `sets`（＋ `sessions`）即時算出，不另存快取或獨立日期表。**
→ 刪掉最後一組後，訓練天數、連續週數、日曆標記、PR 自動正確（避開 VolumeX 刪除後殘留的問題）。
單位內部一律存 kg，顯示時才換算 lb。

## 5. 演算法規格

| 項目 | 規格 |
|---|---|
| e1RM | Epley：`w × (1 + reps/30)`；reps = 1 時取 w（實測 40×10 → 53.3） |
| 單日容量 | Σ（重量 × 次數） |
| PR 判定 | 以動作為單位：最大重量、最大 e1RM、最高單日容量任一超越先前紀錄；首次紀錄視為新高 |
| 累積容量里程碑 | 進度條朝下一階推進：10,000 → 25,000 → 50,000 → 100,000 → 250,000 → 500,000 → 1,000,000 kg（階梯為自訂，原版僅確認首階 10,000） |
| 連續訓練週數 | 以週為單位（週一起算）、該週至少有一場訓練即連續 |
| 本月訓練天數 | 當月有 `sets` 的不重複日期數 |
| BMR | Mifflin–St Jeor |
| TDEE | BMR × PAL（1.2／1.375／1.55／1.725／1.9） |
| 熱量目標 | TDEE × （減脂 0.8／維持 1.0／增肌 1.1） |
| 營養分配 | 蛋白 35%／碳水 25%／脂肪 40%（與 VolumeX 一致），克數＝熱量×比例÷（4／4／9） |
| 熱量由克數算 | `蛋白×4 + 碳水×4 + 脂肪×9`，可手動覆寫 |
| 剩餘可攝取 | 目標 − 已攝取 ＋（設定開啟時）運動消耗 |
| 運動消耗 | `MET × 體重kg × 小時`；重訓 MET 預設 5.0；跑步／走路 ACSM；其他有氧查表；重訓時間＝整場計時器，無計時則每組約 3 分鐘；可手動覆寫 |
| 組間休息 | 預設 60 秒，±30 秒；填入組資料後自動開始；可設定預設值 |

## 6. 畫面與資訊架構

底部分頁：**今日／歷史／計畫／飲食／設定**。

- **今日**：今日課表（來自啟用中週計畫）→「開始訓練」；今日訓練頁（動作卡、Set 列、加減組、全域休息計時、整場計時、新增動作、完成）；每組存檔；PR 觸發慶祝頁；結束後「收操建議」。補記模式沿用現有的日期切換與橘色。
- **動作選擇**：搜尋、器材篩選、肌群分頁（含細分）、最愛、自訂動作（名稱即可）、多選模式（建立課表用）。
- **動作詳情**：教學（GIF、肌群、步驟、提示）、紀錄、圖表（e1RM、容量、最大次數、總次數）、歷史（個人紀錄）。
- **歷史**：容量與有氧分鐘柱狀圖（週／月／年）、力量突破、全年日曆（連續週數、本月天數、本月 kcal、日摘要卡）、今日紀錄彈窗（編輯、刪除、分享圖）。
- **計畫**：週計畫（器材版／出差版切換）、課表範本（複製、刪除、排序、預覽、建立）、新人計畫產生器。
- **飲食**：日期條、熱量與三大營養素進度、記錄飲食（手動、最愛）、運動消耗覆寫、飲食日曆。
- **設定**：單位（體重／重量）、休息預設、消耗計入開關、Health Connect、語言、營養目標、重新計算 TDEE、匯入（Hevy／Strong）、匯出／匯入備份、體重與體脂。

保留 NUO 特色：收操建議（對應課表）、出差模式（紫色）、補記模式（橘色）。

## 7. 專案結構（草案）

```
nuo-workout/
  src/
    data/        # Dexie schema、repositories、遷移、匯出入
    domain/      # 純函式：e1rm、volume、pr、streak、met、tdee、macros（高測試覆蓋）
    features/    # today, history, plans, diet, settings, exercise-picker
    components/  # 共用 UI
    assets/      # 動作 JSON（由 scripts 產生）
  scripts/       # 轉換 VolumeX JSON、合併 NUO 舊動作、複製 GIF 到 www
  android/       # Capacitor 專案
  docs/          # 設計與逆向筆記（私有 repo）
```
舊版單檔 `index.html` 移到 `legacy` 分支保留。

## 8. 風險與緩解（針對方案 B：先全面鋪好再整合）

| 風險 | 緩解 |
|---|---|
| 最後整合才發現資料層與畫面不合 | ① **先完成並測完資料層與 domain 純函式**（這是畫面唯一的依據）② 畫面框架一律接同一套 repository 介面，先接記憶體假資料③ 每個畫面完成後立刻用同一份假資料跑起來看過 |
| 長時間沒有可用版本 | 舊 NUO 繼續使用；中途設幾個「可跑檢查點」（資料層全綠、所有畫面可點通）｜每個檢查點都 `adb install` 一次確認不崩潰 |
| 統計算式出錯 | domain 層每個公式以實測數據點寫測試（Epley 40×10＝53.3、容量 400、TDEE 係數、營養分配 35/25/40 → 164/117/83 g 等） |
| 動作資料體積（369 MB GIF） | 不進 git；建置腳本複製；APK 約 400 MB 自用可接受，之後可改 WebP |
| 資料遺失 | 匯出／匯入 JSON、系統自動備份、更新前提醒匯出 |
| 著作權 | 動作資料與 GIF 僅限私人 repo／自用，不公開、不上架（使用者已知悉並同意） |

## 9. 實作順序（方案 B）

1. **基礎**：Vite + TS + Preact + Dexie + Capacitor 專案骨架、`legacy` 分支、建置腳本（轉動作 JSON、併入 NUO 舊動作、複製 GIF）。
2. **資料層**：schema、repositories、匯出入、遷移＋ domain 純函式與測試。
3. **畫面框架**：底部分頁與全部畫面（今日、動作選擇、動作詳情、歷史、計畫、飲食、設定），先用假資料。
4. **整合**：接上資料層，逐流程串通（首次問卷 → 週計畫 → 今日訓練 → PR 慶祝 → 歷史與日曆 → 飲食）。
5. **打包與驗證**：Capacitor 打包、無線偵錯安裝、手機上走完整流程。
6. **匯入與收尾**：Hevy／Strong CSV、新人計畫、備份驗證、效能與細節。
